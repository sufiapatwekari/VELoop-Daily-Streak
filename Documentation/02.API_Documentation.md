# VELoop Rewards — API Documentation

## 1. API Overview

The VELoop Rewards backend provides APIs for user authentication, daily streaks, rewards, wallet balance, transactions, and streak history.

Backend URL:

http://localhost:5000

The APIs use standard HTTP methods such as `GET` and `POST`.

---

# 2. Authentication

Protected APIs require a valid JWT token.

Add the token to the request header:


Authorization: Bearer <JWT_TOKEN>

The backend uses the token to identify the logged-in user.

---

# 3. Common HTTP Status Codes

| Status Code | Meaning                                     |
| ----------- | ------------------------------------------- |
| 200         | Request completed successfully              |
| 201         | Resource created successfully               |
| 400         | Invalid request or claim not allowed        |
| 401         | Authentication required or token is invalid |
| 404         | Requested data was not found                |
| 429         | Too many requests                           |
| 500         | Server error                                |

---

# 4. User Registration

## Endpoint


POST /register


## Purpose

Creates a new user account.

## Request Body

{
  "name": "Test User",
  "email": "test@example.com",
  "password": "password123"
}


## Main Validation

* Name is required.
* Email is required.
* Email is stored in lowercase.
* Password must meet the minimum length requirement.
* The email must not already exist.

## Successful Response

Example:

{
  "message": "User registered successfully"
}


A wallet and streak record are created for the new user.

---

# 5. User Login

## Endpoint

POST /login

## Purpose

Checks the user's email and password and returns a JWT token.

## Request Body

{
  "email": "test@example.com",
  "password": "password123"
}


## Successful Response

Example:

{
  "message": "Login successful",
  "token": "<JWT_TOKEN>"
}


The token is used for protected API requests.

---

# 6. Get User Profile

## Endpoint

GET /profile

## Authentication

Required.

Authorization: Bearer <JWT_TOKEN>

## Purpose

Returns information about the currently logged-in user.

## Example Response

{
  "id": "<USER_ID>",
  "name": "Test User",
  "email": "test@example.com"
}


The profile API does not contain the old `gemBalance` field.

The current VES balance is available through the wallet API.

---

# 7. Get Streak Status

## Endpoint


GET /streak/status


## Authentication

Required.

## Purpose

Returns the current streak and reward information for the logged-in user.

## Example Response

{
  "currentStreak": 1,
  "longestStreak": 1,
  "currentDay": 1,
  "totalRewards": 7,
  "checkedIn": 1,
  "nextReward": "+10 VES",
  "nextRewardDay": 2,
  "vesBalance": 5,
  "todayClaimed": true,
  "nextClaimAt": "2026-10-07T10:00:00.000Z",
  "serverTime": "2026-10-06T10:00:00.000Z",
  "rewards": []
}


The exact time and reward status values change according to the user's current streak.

## Main Response Fields

| Field           | Description                                  |
| --------------- | -------------------------------------------- |
| `currentStreak` | Current consecutive streak                   |
| `longestStreak` | User's highest streak                        |
| `currentDay`    | Current day in the 7-day cycle               |
| `totalRewards`  | Total rewards in the cycle                   |
| `checkedIn`     | Number of completed check-ins                |
| `nextReward`    | Next available reward                        |
| `nextRewardDay` | Day of the next reward                       |
| `vesBalance`    | Current VES wallet balance                   |
| `todayClaimed`  | Whether the current claim has been completed |
| `nextClaimAt`   | Time when the next claim can be made         |
| `serverTime`    | Current backend time                         |
| `rewards`       | Reward status for the seven-day cycle        |

# 8. Claim Daily Reward

## Endpoint

POST /streak/claim


## Authentication

Required.

## Request Body

No request body is required.

{}


The user does not send:

* Day number
* Reward amount
* Streak number
* User ID

The backend gets these values from the authenticated user and database.

---

# 9. Claim Validation

Before giving a reward, the backend checks:

1. User authentication
2. User's streak
3. Current claim time
4. Previous claim
5. Correct streak day
6. Duplicate claim
7. Reward configuration
8. Wallet update, when required

If any required check fails, the reward is not given.

---

# 10. Successful Claim

Example:

{
  "message": "Reward claimed successfully",
  "streak": 1,
  "day": 1,
  "reward": {
    "rewardType": "VES",
    "amount": 5,
    "currency": "VES"
  },
  "vesBalance": 5,
  "lastClaimDate": "2026-10-06T10:00:00.000Z"
}


The actual values depend on the user's current day and reward.

For example:

Day 1 → +5 VES
Day 2 → +10 VES
Day 3 → +15 VES
Day 4 → ₹1 Amazon Gift Card
Day 5 → ₹2 Amazon Gift Card
Day 6 → +30 VES
Day 7 → ₹5 Amazon Gift Card


---

# 11. Claim Errors

### Claim made too early

If 24 hours have not passed:

{
  "message": "Please wait before claiming again"
}

Status:

400 Bad Request

---

### Previous day not completed

If the user tries to skip a day:

{
  "message": "Previous day must be completed first"
}

Status:

400 Bad Request

---

### Duplicate claim

If the user has already claimed the current reward:

{
  "message": "Reward already claimed"
}


Status:

400 Bad Request


---

### Authentication error

If the JWT token is missing or invalid:

{
  "message": "Unauthorized"
}

Status:

401 Unauthorized

---

### Rate limit

If too many claim requests are sent:

{
  "message": "Too many requests"
}

Status:

429 Too Many Requests

# 17. Seven-Day Reward Configuration

The current reward configuration is:

| Day | Reward Type | Reward |
| --- | ----------- | -----: |
| 1   | VES         |  5 VES |
| 2   | VES         | 10 VES |
| 3   | VES         | 15 VES |
| 4   | Gift Card   |     ₹1 |
| 5   | Gift Card   |     ₹2 |
| 6   | VES         | 30 VES |
| 7   | Gift Card   |     ₹5 |

The reward values are stored in the backend database.

The frontend does not decide these values.

---

# 18. Claim Timing

The system uses a 24-hour claim interval.

The backend provides:

serverTime
nextClaimAt

The frontend uses these values to show the countdown.

The actual claim permission is checked again by the backend when the user clicks the claim button.

---

# 19. Missed-Day Reset

The system uses a 48-hour missed reset rule.

If the user misses the allowed claim period and reaches the reset limit, the backend starts a new streak cycle.

The user starts again from:

Day 1

The reset information is stored in the database.

---

# 20. Database Records Created After a Successful Claim

A successful claim can update or create records in:


Wallet
Transaction
Streak
StreakHistory
AuditLog


This keeps the wallet, streak and history information connected.

---

# 21. API Security

The claim API is protected using authentication and rate limiting.

The backend does not trust day, reward, streak, or user values sent by the frontend.

For example, a request such as:

{
  "day": 7,
  "reward": 1000
}


does not make the backend give a Day 7 reward of 1000.

The backend gets the correct reward from the reward configuration stored in MongoDB.

# 22. Development and Testing APIs

The project also contains some endpoints used during local development and testing, such as:

POST /streak-config/setup
POST /rewards/setup
POST /test/reset-streak
POST /test/advance-day
POST /test-user
GET  /test/streak-history-indexes
POST /test/create-streak-history-index


These endpoints are intended for development/testing only.

They should not be exposed as normal public APIs in a production deployment.

For the final production version, these should be removed, disabled, or protected with proper admin/development checks.

   ↓

   ↓

---

# 24. Final API Rule

The main rule of the API is:

> The client requests a reward, but the backend decides whether the reward can be given.

The frontend only displays the result returned by the backend.
