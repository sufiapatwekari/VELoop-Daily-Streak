# VELoop Rewards — Database Design

## 1. Database Overview

VELoop Rewards uses "MongoDB" as its database.

MongoDB stores data in collections, and each record is stored as a document.

The backend uses "Mongoose" to define and work with the database models.

The database stores:

* User accounts
* Wallet balance
* Streak information
* Reward configuration
* Streak history
* Transactions
* Audit logs

The database is hosted using "MongoDB Atlas".

# 3. Database Relationship

The main relationships are:

```text
                         ┌──────────────┐
                         │    User      │
                         └──────┬───────┘
                                │
              ┌─────────────────┼─────────────────┐
              │                 │                 │
              ↓                 ↓                 ↓
        ┌──────────┐      ┌──────────┐      ┌──────────────┐
        │  Wallet  │      │  Streak  │      │ Transactions │
        └──────────┘      └─────┬────┘      └──────────────┘
                                │
                                ↓
                       ┌────────────────┐
                       │ Streak History │
                       └────────────────┘

        User ───────────────→ Audit Logs

        Streak Config ──────→ Reward Config
```

A user has one wallet and one active streak record.

A user can have many transaction, streak history, and audit log records.

The reward and streak configuration are shared configuration data.

MongoDB supports both one-to-one and one-to-many relationship models using references or embedded documents. This project mainly uses separate collections connected through IDs.

# 4. Users Collection

## Collection

```text
users
```

## Purpose

Stores the basic information of registered users.

## Main Fields

| Field      | Type     | Description     |
| ---------- | -------- | --------------- |
| `_id`      | ObjectId | Unique user ID  |
| `name`     | String   | User name       |
| `email`    | String   | User email      |
| `password` | String   | Hashed password |

### Example

```json
{
  "_id": "<USER_ID>",
  "name": "Test User",
  "email": "test@example.com",
  "password": "<HASHED_PASSWORD>"
}
```

The password is stored as a hash and not as plain text.

The email is normalized before storing/checking the user.

# 5. Wallets Collection

## Collection

```text
wallets
```

## Purpose

Stores the user's VES balance.

## Main Fields

| Field        | Type     | Description         |
| ------------ | -------- | ------------------- |
| `_id`        | ObjectId | Wallet ID           |
| `userId`     | ObjectId | Related user        |
| `vesBalance` | Number   | Current VES balance |

### Example

```json
{
  "_id": "<WALLET_ID>",
  "userId": "<USER_ID>",
  "vesBalance": 5
}
```

Each user has one wallet.

The `userId` field is unique so that the same user does not have multiple wallet records.

# 11. Streak History Index

The project uses a unique rule to help prevent the same day from being marked as claimed more than once in the same cycle.

The important fields are:

```text
userId
cycleId
day
status
```

The unique rule applies to claimed records.

This provides an additional database-level check against duplicate claims.

Indexes are useful for fields that are frequently searched or filtered. MongoDB recommends creating indexes based on the queries used by the application.

# 15. Streak Cycle

The project uses a `cycleId` to separate different seven-day streak cycles.

For example:

```text
Cycle 1
Day 1
Day 2
Day 3
Day 4
Day 5
Day 6
Day 7
```

If the user completes the cycle or the streak is reset, a new cycle can be started.

This prevents history from different cycles from being treated as the same set of claims.

# 16. Successful Claim Database Flow

When a user successfully claims a reward, the backend can update several collections.

```text
User
  ↓
Streak
  ↓
Reward
  ↓
Wallet
  ↓
Transaction
  ↓
StreakHistory
  ↓
AuditLog
```

For a VES reward:

```text
Old Wallet Balance
       ↓
Add VES Reward
       ↓
New Wallet Balance
       ↓
Create Transaction
       ↓
Save Streak History
       ↓
Save Audit Log
```

The claim process uses a MongoDB transaction so related changes can be handled together. MongoDB supports multi-document transactions for operations that need changes across multiple collections to stay consistent.

# 18. Duplicate Claim Protection

The database structure helps prevent duplicate claims.

For example:

```text
User A
Cycle 1
Day 1
CLAIMED
```

A second successful Day 1 record should not be created for the same cycle.

The backend checks the claim before updating the wallet and history.

The database index provides another level of protection.

# 19. Database Timestamps

Where timestamps are enabled in the Mongoose models, the database records can store:

```text
createdAt
updatedAt
```

Date fields such as `lastClaimDate` and `claimedAt` are used for streak timing and history.

Only models that actually use Mongoose timestamps should be described as having automatic `createdAt` and `updatedAt` fields.

# 22. Why Separate Collections Are Used

The project keeps wallet, streak, history, transaction, and audit information in separate collections.

This makes it easier to:

* Find a user's current wallet
* Get the current streak
* Show claim history
* Show transactions
* Record audit information
* Update different types of data separately

The structure also keeps frequently changing data such as wallet and streak information separate from reward configuration.

---

# 23. Database Safety

Important database rules include:

* User email should be unique.
* User wallet should be unique per user.
* Active streak should be unique per user.
* Claimed streak day should not be duplicated within the same cycle.
* User-specific records should use the authenticated user ID.
* Reward values should come from the reward collection.
* Database credentials should not be stored in source code.

---

# 24. Main Database Summary

The database can be summarized as:

```text
users
 ├── wallets
 ├── streaks
 ├── streakhistories
 ├── transactions
 └── auditlogs

streakconfigs
 └── rewards
```

The `users` collection stores account information.

The `wallets` collection stores VES balance.

The `streaks` collection stores the current streak.

The `streakhistories` collection stores previous claims.

The `transactions` collection stores reward-related wallet changes.

The `auditlogs` collection stores important system actions.

The `streakconfigs` and `rewards` collections store the rules and rewards for the daily streak system.

---

# 25. Final Database Principle

>The database stores the actual state of the VELoop reward system.

The frontend only displays the data returned by the backend.

The backend reads and updates MongoDB when the user registers, logs in, checks the streak, claims a reward, receives VES, or views their history.

This keeps the user's streak, rewards, wallet and transaction information stored even after the browser is refreshed or closed.
