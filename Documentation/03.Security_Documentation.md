# VELoop Rewards — Security Documentation

## 1. Security Overview

Security is an important part of the VELoop Rewards project.

The main security rule is:

> The browser is not trusted to decide important reward information.

The frontend can display information and send requests, but the backend checks the user's identity, streak, reward, claim time, and wallet before making any changes.

This helps prevent users from changing values through the browser to get rewards they have not earned.

---

# 2. Security Features

The project includes the following security measures:

* Password hashing
* JWT authentication
* Protected backend routes
* User-specific database queries
* Backend-controlled streak days
* Backend-controlled rewards
* Server-side claim time validation
* Duplicate claim protection
* Concurrent claim protection
* Rate limiting
* Audit logs
* Input validation
* Environment variables for sensitive configuration

---

# 3. Password Security

User passwords are not stored as plain text.

The project uses **bcrypt** to hash passwords before storing them in MongoDB.

Example:

```text
User enters password
       ↓
bcrypt hashes password
       ↓
Hashed password stored in MongoDB
```

During login, the entered password is compared with the stored hash.

Using a password hashing algorithm such as bcrypt is a recommended approach for storing passwords safely.

---

# 4. JWT Authentication

After successful login, the backend generates a JWT token.

The frontend sends the token with protected API requests:

```text
Authorization: Bearer <JWT_TOKEN>
```

The authentication middleware checks the token before allowing access to protected routes.

The backend gets the user ID from the authenticated token.

Example:

```text
Login
  ↓
JWT generated
  ↓
Frontend stores token
  ↓
Token sent with protected request
  ↓
Backend verifies token
  ↓
User ID identified
```

The JWT secret is stored in an environment variable instead of being written directly in the source code.

JWT secrets should be kept private and should not be published.

---

# 5. User-Specific Data

After authentication, the backend uses the logged-in user's ID when accessing user data.

For example:

```text
User A → User A's streak
User A → User A's wallet
User A → User A's transactions

User B → User B's streak
User B → User B's wallet
User B → User B's transactions
```

A user should not be able to access another user's wallet or streak by simply changing an ID in the request.

---

# 6. Backend Controls the Streak

The frontend does not decide the current streak day.

For example, the frontend cannot simply send:

```json
{
  "day": 7
}
```

and receive the Day 7 reward.

The backend gets the user's current streak information from MongoDB and checks the correct day.

The backend decides:

* Current streak
* Current day
* Previous claim
* Next claim time
* Claim eligibility
* Missed-day reset
* Reward

---

# 7. Backend Controls the Reward

The reward amount is stored in the `rewards` collection.

The frontend does not decide the reward amount.

For example, changing a request to:

```json
{
  "reward": 1000
}
```

does not give the user 1000 VES.

The backend gets the correct reward from the database.

This prevents simple frontend changes from changing the actual reward.

---

# 8. Claim Timing Protection

The project uses a 24-hour claim interval.

The backend checks the previous claim time before allowing a new claim.

Example:

```text
Last claim
    ↓
Wait 24 hours
    ↓
Backend checks time
    ↓
Claim allowed
```

If the user tries to claim too early, the backend rejects the request.

The frontend countdown is only for display. The backend performs the final time check.

---

# 9. Sequential Day Protection

Users must complete the days in order.

For example:

```text
Day 1 → Day 2 → Day 3 → Day 4
```

A user cannot directly request Day 4 without completing the required previous day.

The backend checks the current streak and previous claim before allowing the reward.

---

# 10. Duplicate Claim Protection

The backend checks whether the current day's reward has already been claimed.

For example:

```text
First request
    ↓
Claim successful

Second request
    ↓
Backend checks history
    ↓
Claim rejected
```

This prevents the same reward from being added more than once.

The database also uses a unique rule for claimed streak records to provide an additional check.

---

# 11. Concurrent Claim Protection

The project also handles multiple claim requests sent at nearly the same time.

For example:

```text
Request 1 ─┐
           ├── Backend
Request 2 ─┘
```

The claim process uses a MongoDB transaction so that related database changes are handled together.

This helps prevent two requests from giving the same reward.

---

# 12. Wallet Protection

The VES wallet is updated by the backend.

For a VES reward:

```text
Old Balance
     ↓
Add Reward
     ↓
New Balance
```

Example:

```text
0 VES + 5 VES = 5 VES
```

The frontend cannot directly update the wallet balance.

The wallet update is connected with the transaction and streak claim process.

---

# 13. Transaction Records

When a VES reward is successfully given, the system creates a transaction record.

The transaction can contain:

* User ID
* Transaction ID
* Reward type
* Amount
* Currency
* Source
* Streak day
* Balance before
* Balance after
* Status

Example:

```text
Balance Before: 0 VES
Reward: +5 VES
Balance After: 5 VES
Source: DAILY_STREAK
Status: SUCCESS
```

This makes it easier to check how the wallet balance changed.

---

# 14. Audit Logs

The project uses an `AuditLog` collection for important streak actions.

Examples include:

* `STREAK_CLAIM_REQUEST`
* `SUCCESS`
* `REJECTED`
* `DUPLICATE_CLAIM`
* `RESET`
* `INVALID_CLAIM`

Audit logs help during testing and debugging because important actions can be checked later.

---

# 15. Rate Limiting

The claim API has rate limiting.

The current claim endpoint allows a limited number of requests within a fixed time period.

If too many requests are made, the API returns:

```text
429 Too Many Requests
```

This helps reduce repeated automated requests to the claim endpoint.

Rate limiting is a common protection for APIs and should also be considered for authentication endpoints in a production system.

---

# 16. Input Validation

The backend validates important user input.

For registration, the main checks include:

* Name
* Email
* Password
* Duplicate email

The email is normalized before checking the database.

The password must meet the minimum length required by the application.

More detailed input validation can be added for a production deployment.

---

# 17. Environment Variables

Sensitive configuration is kept in environment variables.

Example:

```env
PORT=5000
MONGO_URI=your_mongodb_connection_string
JWT_SECRET=your_jwt_secret
```

These values should not be written directly inside the source code.

The real `.env` file should not be uploaded to GitHub or included in the final project ZIP.

Instead, the project can include:

```text
.env.example
```

with placeholder values.

Secrets and keys should not be committed to source repositories.

---

# 18. MongoDB Security

MongoDB Atlas is used for database storage.

The application connects to MongoDB using the connection string stored in the environment configuration.

Database credentials should remain private.

The MongoDB Atlas user should have only the permissions needed by the application.

---

# 19. CORS

During local development, the backend allows requests from the frontend development URL.

Example:

```text
http://localhost:5173
```

For production, the allowed frontend domain should be configured using an environment variable instead of keeping a development URL in the code.

---

# 20. Development and Testing Endpoints

The project contains some endpoints used during development and testing.

Examples:

```text
/streak-config/setup
/rewards/setup
/test/reset-streak
/test/advance-day
/test-user
```

These endpoints are useful during local testing, but they should not be available to normal users in a production deployment.

For production, they should be:

* Removed, or
* Disabled, or
* Protected using proper admin/development checks.

---

# 21. Error Messages

The API should return simple error messages to the client.

For example:

```json
{
  "message": "Unauthorized"
}
```

The client does not need database details, internal errors, or sensitive configuration information.

For production, detailed server errors should be logged on the backend while the user receives a simple message.

---

# 22. JWT Storage

The current frontend uses a token-based authentication flow.

For the internship project, the JWT is handled on the frontend and sent with protected API requests.

For a production application, a safer approach can be considered, such as using secure HTTP-only cookies.

Storing authentication tokens in browser storage has security risks, especially if the application has an XSS vulnerability.

---

# 23. HTTPS

The local project uses HTTP because it runs on localhost.

For production deployment, HTTPS should be used for login and authenticated requests.

This protects passwords and authentication tokens while they are being transferred between the browser and server.

---

# 24. Security Testing

The following security-related tests were performed:

| Test                    | Expected Result                        |
| ----------------------- | -------------------------------------- |
| Missing JWT             | Request rejected                       |
| Invalid JWT             | Request rejected                       |
| Fake user ID            | User cannot access another user's data |
| Fake day                | Backend ignores the fake day           |
| Fake reward             | Backend uses the database reward       |
| Duplicate claim         | Second claim rejected                  |
| Multiple claim requests | Only valid claim succeeds              |
| Claim too early         | Request rejected                       |
| Changed device time     | Backend still checks its own time      |
| Missed day              | Streak reset according to the rule     |
| Too many claim requests | Rate limit applied                     |
| Browser refresh         | Streak remains unchanged               |

# 25. Important Security Checklist

Before submitting or deploying the project:

* [ ] Remove the real `.env` file from the submission if it contains secrets.
* [ ] Add `.env` to `.gitignore`.
* [ ] Keep `.env.example` with placeholder values.
* [ ] Do not share the MongoDB password.
* [ ] Do not share the JWT secret.
* [ ] Disable development/test endpoints for production.
* [ ] Check that users cannot access another user's data.
* [ ] Test duplicate claims.
* [ ] Test fake reward values.
* [ ] Test fake day values.
* [ ] Test invalid JWT tokens.
* [ ] Use HTTPS in production.
* [ ] Configure production CORS correctly.

If real database credentials or JWT secrets have already been shared publicly, they should be changed before deployment.

---

# 26. Known Limitations

The following are limitations of the current internship project:

1. Automated security testing is not included.
2. Development/testing endpoints are available for local testing and should be disabled before production.
3. Login and registration can have stronger rate limiting in a production version.
4. The current frontend token handling can be improved using secure HTTP-only cookies.
5. HTTPS is required when deploying the application publicly.
6. Additional security headers and monitoring can be added for a production deployment.

# 28. Final Security Principle

The main security principle of VELoop Rewards is:

> The frontend can request a reward, but only the backend can approve and record it.

The backend checks the user, streak, claim time, reward, wallet and database records before completing the claim.

This keeps the important reward logic on the server instead of trusting values sent by the browser.
